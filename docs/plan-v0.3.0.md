## 一、结论与当前代码基础

需求总体可行，可以继续采用“麒麟上一台本地服务、多台办公电脑通过浏览器访问”的方式，不要求工作电脑联网，也不要求客户端安装软件。这次升级涉及身份、机构权限、正式数据、草稿、复核、审计和导入事务，是一次业务底座升级，不能仅在现有页面上添加按钮。

建议协作方式：公共基础先串行落地并合并；随后两条业务线并行；最后统一联调、迁移验证和打包。不是两个人同时修改现有所有文件，也不是一个人做完所有功能另一个人才开始。

### 1.1 原 V0.2.2 基线（历史情况，不是 PR0.5 现状）

| 现有代码 | 已有能力 | 对本次需求的影响 |
| --- | --- | --- |
| `src/AuthService.java` | 单个管理员密码、会话、密码校验、基础防重复尝试 | 没有用户身份、姓名、角色或机构，必须升级为多用户认证 |
| `src/Main.java` | 首页、明细、支行页、导出、上传、填写路由集中在一个类 | 目前业务查看及填写不是基于实名账号授权，需统一加服务端访问控制 |
| `src/DataStore.java` | 按月份和批次保存 `.rows`、`.properties`；同类同一期更新 | 没有独立草稿、审批单、行版本和事务审计；上传与填写存在覆盖风险 |
| `src/Model.java` | 工作簿、列、行等结构 | 当前批次 ID 加行号不适合作为跨导入、跨审批的稳定记录标识 |
| `src/Html.java`、`web/assets/style.css` | 页面与样式集中管理 | 两个 AI 直接并行编辑容易产生合并冲突，需先拆模块 |
| `src/DashboardData.java` | 时间筛选、统计、机构聚合及完成情况 | 机构来自导入表，不是固定维护的九家支行名单 |
| `packaging/build_offline.ps1` | 本地离线包构建 | 依赖本机 `smart_excel` 路径，GitHub 环境不能直接复现；应先修复开发构建入口 |

九家支行名称已由用户确认，当前稳定内部 ID 和名称映射见 Organizations；这些内部 ID 不代表已经对接行内正式机构编码。新增别名仍须核实。不得把未知机构自动归属某家支行，也不得用“其他”绕过权限归属。

### 1.2 建议保留与调整

- 保留 Java 服务端、服务端生成 HTML、本地静态资源、离线部署和原有年度／季度／月份／自定义月份区间。
- 不引入必须联网的前端组件、在线字体、在线图标或大模型接口。本轮功能不需要大模型。
- 建议将核心持久化改为嵌入式关系数据库，首选评估 H2：用户、草稿、复核和正式数据可以在同一事务内维护；使用嵌入模式，不开放数据库管理端口或 Web Console。H2 支持 Java、嵌入模式和事务，适合作为本项目的候选方案；具体依赖版本需在基础 PR 中固定并测试。[H2 官方功能说明](https://h2database.github.io/html/features.html)
- 应用仍是一套服务，嵌入数据库不要求你另外手工安装数据库服务。实际麒麟架构、JDK、文件权限和关闭服务时的数据一致性仍需实机验证。
- 源码开发环境可联网取得固定版本依赖；交付到工作电脑的安装包必须包含运行所需全部依赖，安装与启动不得下载任何内容。

## 二、需求逐项分析与实施步骤

### R01：五类角色与人员管理

角色固定为：超级管理员、分行管理员、支行管理员、客户经理操作员、客户经理复核员。第一版建议一人一个角色、一人一个所属机构，不引入多角色叠加，避免出现权限组合歧义。

| 角色 | 业务查看范围 | 人员管理范围 | 填写／修改业务数据 | 审核操作员提交 | 上传表格 |
| --- | --- | --- | --- | --- | --- |
| 超级管理员 | 全部分行及支行数据 | 分行管理员、各支行管理员、操作员、复核员 | 不允许 | 默认不允许，仅查看 | 不允许 |
| 分行管理员 | 全部数据 | 各支行管理员及各支行操作员、复核员 | 允许，确认提交后直接生效 | 默认不代替支行复核员审批 | 允许 |
| 支行管理员 | 仅本支行 | 仅本支行操作员、复核员 | 允许，确认提交后直接生效 | 默认不代替复核员审批 | 不允许 |
| 客户经理操作员 | 仅本支行 | 无 | 保存草稿、提交复核，通过后生效 | 不允许 | 不允许 |
| 客户经理复核员 | 仅本支行 | 无 | 本人修改确认提交后直接生效 | 允许，仅本支行 | 不允许 |

“上级管理”不等于拥有下级所有业务操作：超级管理员只读业务、只有分行管理员上传，是用户明确指定的例外，必须用权限表表达，不能简单按角色大小比较。分行／支行管理员的直接修改也不能冒充对某个操作员审批单的批准。

实施步骤：

1. 创建机构表，包含分行及九家支行，使用稳定机构 ID；建立导入名称到机构 ID 的别名映射。
2. 创建用户表，包含内部用户 ID、统一认证号、姓名、角色、机构、状态、密码哈希、首次改密标记等。
3. 建立“允许管理的目标角色＋允许管理的机构范围”规则；同级管理员互相管理默认不开放，自身资料与密码走独立入口。
4. 按角色显示人员管理按钮、人员列表和可选角色。支行管理员新增时机构锁定本支行；分行管理员创建支行角色时必须指定目标支行。
5. 实现新增、查看、修改、停用／删除、密码重置。界面可叫删除，底层建议逻辑删除，不清除历史操作记录，不复用已经使用过的统一认证号。
6. 修改角色、机构或停用账号后使旧会话失效；禁止通过修改表单参数提升自己权限。转机构前提示未完成草稿和审批事项，不自动把业务记录转移到新机构。
7. 超级管理员初始账号通过部署端一次性设置，使用用户本人提供的统一认证号和姓名；不在公网注册入口创建超级管理员。禁止删除最后一个有效超级管理员。

验收：支行管理员无法创建分行管理员、修改其他支行用户或把自己升级；停用账号立即不能继续访问；旧记录仍能查到实际操作人。

### R02：统一认证号登录、随机初始密码和首次改密

这里的“统一认证号”先作为本系统的登录账号，不代表已经对接行内统一认证系统或自动验证员工身份；真正接入统一认证需要另行取得接口与授权。

实施步骤：

1. 登录页改为统一认证号、密码，并提供申请权限入口。
2. 管理员添加用户成功后，用安全随机数生成初始密码；建议只展示一次，由管理员通过行内认可方式单独通知本人。
3. 数据库只存加盐密码哈希，不保存可查看的明文密码；日志、通知和导出不包含密码。
4. 除超级管理员外，新用户首次登录和管理员重置密码后强制改密；未改密会话只允许改密及退出，不能直接输入明细 URL 绕过。
5. 改密成功后进入本次登录的数据安全提示，确认后才能访问业务页。
6. 提供本人修改密码和有权限管理员重置下级密码；保留账号级及访问来源级的失败限制，明确“修改成功”“已过期”等反馈。

验收：超级管理员首次登录直接进入首页，其他新用户不能跳过改密；初始密码失效后无法再次使用；其他管理员不能查询用户现用密码。

### R03：申请权限与审批开户

按用户描述，申请人填写机构、统一认证号、姓名，不自行授予角色。建议由审批人在自己可授权范围内选择最终角色。

| 申请类型 | 接收人 | 建议审批规则 |
| --- | --- | --- |
| 选择分行 | 超级管理员 | 确认身份后，决定是否开通分行管理员；不开放超级管理员自助申请 |
| 选择具体支行 | 该支行管理员 | 可批准为本支行操作员或复核员 |
| 需要支行管理员身份 | 分行管理员 | 支行管理员不能批准与自己同级的身份，可转交分行审批 |
| 该支行暂时没有管理员 | 分行管理员 | 兜底处理，避免申请没有接收人 |

实施步骤：

1. 申请页提供“分行／支行”二选一；选支行后必须从正式机构列表选择，禁止自由填写机构。
2. 校验统一认证号格式、已开户与待审重复申请，防止反复提交制造重复账号。
3. 申请生成唯一申请单，记录机构、申请人、时间、状态和审批人范围，发送站内通知。
4. 管理员打开申请详情，确认身份、角色和机构后同意、拒绝或按授权范围转交；拒绝记录原因。
5. 审批同意时，申请状态更新、账号创建、初始密码生成及审计记录一起完成，重复点击不能生成两个人员账号。
6. 生成的是“申请人的初始密码”，不是审批人自己的密码；由审批管理员自行发送给申请人。

申请人此时可能尚无可登录账号，审批结果及初始密码交付不能依赖其站内消息中心；由管理员人工通知。若审批成功页面的初始密码未妥善记录，走密码重置流程，不提供反复查看明文的接口。

验收：同一申请被两位管理员同时处理，只能有一次有效审批；支行管理员不能利用开户流程新增其他支行人员。

### R04：消息提醒与红色数字气泡

通知与待办应分开：已读只说明看过消息，不代表已经审批。红色气泡按当前账号的未读通知条数显示，不把全系统或全支行通知混在一起。

实施步骤：

1. 建立通知事件和接收人记录，分别保存每个接收人的已读时间。
2. 接入权限申请、开户审批结果、操作员提交、复核通过、退回等事件。
3. 右上角增加消息按钮、未读数和列表；从通知跳转详情时仍执行权限校验。
4. 消息内容提供“谁、哪张表、哪一期、修改几条”，详细字段内容在授权详情页展示，通知中不携带密码。
5. 同一支行有多个复核员时，均可收到待办提醒；第一位完成有效审批后，其他人打开应看到已处理及处理人，不得重复生效。
6. 首版采用页面加载刷新消息数，兼容环境可增加轻量定时查询；不依赖浏览器推送或联网通知服务。

验收：未读数只计本人的通知；跨支行访问通知详情失败；已读的待办未审批时仍保留在待办列表。

### R05：所有入口背对背隔离

实施步骤：

1. 登录会话只保存用户标识等最小信息，由服务端根据有效用户记录计算数据范围。
2. 所有业务查询强制带机构范围。超级／分行管理员为全部范围；支行三类角色固定为自己的机构。
3. 将过滤落实到数据访问／业务服务层，而不只是隐藏网页按钮。浏览器提交的支行参数最多用于缩小授权范围，不能扩大范围。
4. 覆盖首页总数、进度、机构分布、时间选项、搜索、两个清单、行内数据、导出、草稿、变更预览、复核、日志和通知。
5. 导出不能先生成全行 Excel 再隐藏其他支行行；必须只取授权数据，并排除未授权隐藏 Sheet、缓存内容。
6. 原有查看、填写和导出 URL 同样纳入校验；旧的匿名表单会话不能继续作为业务写入凭证。
7. 所有变更操作使用 POST 并校验会话和 CSRF 令牌；不能仅依赖旧浏览器可能不支持的 Cookie 属性。差异、通知和日志里的表格文本统一转义，防止用户输入或 Excel 内容被当成网页脚本。

验收：用甲支行账号修改 URL、记录 ID、导出参数、提交体访问乙支行数据均失败；甲支行首页统计数字中不包含乙支行数据。

### R06：首页、清单、时间筛选和宽度

实施步骤：

1. 删除首页趋势图和行业分布图，不删除原始行业字段。保留总统计、总资料补充进度、机构分布及机构进度；其他现有图表不因本次需求擅自扩大删除范围。
2. 超级／分行管理员首页显示全行视图；支行三类角色默认显示本支行视图，不能出现全行汇总数字。
3. 首页“多重预警”“负面闭环”仅显示未完成的正式记录；点击“查看全部”进入完整清单，默认包含已完成与未完成。
4. 完整清单提供全部／未完成／已完成筛选，与年度、季度、月份、自定义月份区间、搜索条件组合使用。
5. 从首页进入明细、查看全部、导出时保留当前时间和机构条件；资料补充进度按所选范围的全部正式记录计算，而不是仅按首页未完成预览计算。
6. 明细区采用接近窗口宽度的布局，例如约 96%，减少两侧空白；表格本身保留横向滚动，长文本列设置合理宽度并换行。1366 和 1920 宽度分别验收。
7. 编辑区仍是顶部统一操作按钮，不回到每单元格一个保存；翻页前提醒未保存内容，已保存草稿可以跨页恢复。
8. 右上角保留最近正式数据更新时间和版本号；保存草稿不能冒充正式数据已经更新。支行视图的更新时间只根据本支行可见数据计算。

验收：完成一条正式记录后，其在首页未完成预览消失、完整清单仍可查；进度分母不因隐藏完成行缩小；窄屏不截断按钮。

### R07：完成口径与行底色（按新模板及最新确认）

当前生效规则：一行任意黄色填报单元格有非空内容即为完成；来源字段不计，空白／纯空格不计，0 和“否”计入。多重 I–P、R–V；负面 J–L；交叉 M–O。不要恢复旧方案的“所有必填项齐全”或“无风险视为完成”规则。

- 正式已完成记录的来源单元格淡绿色；未完成记录白色；黄色填报列保持黄色。
- 首页只显示未完成正式记录，完整清单和导出仍可查询全部；草稿和待复核值以后也不得提前计入完成率。
- 无风险功能按用户最新要求暂不开发，后续只有重新确认才纳入范围。
- 新模板尚无独立反馈截止字段，不从其他日期猜测，不计算反馈超时或标红。
- 未来补充截止字段后，再确认按提交时间还是审批生效时间衡量超时，并统一机构、时区和状态规则。

验收：任填一个黄色格即完成，清空最后一个已填黄色格后恢复未完成；首页、正式统计和导出使用 DatasetSchema.complete 的同一口径。当前验收不包含无风险与截止超时。

### R08：操作员草稿、差异预览、提交和复核

建议以“变更单”承载一次提交：包含同一机构、同一数据集内本次修改的多条记录，仅记录真正变化的字段。跨模块操作分别生成变更单，降低误批范围。

实施步骤：

1. 每条正式记录增加稳定记录 ID 和版本号；草稿另外保存，不直接写正式字段。
2. 操作员修改后点击“保存草稿”，保存到服务器并绑定本人账号，重新登录仍可恢复。默认不把某人的未提交草稿当成其他人的可见正式内容。
3. 点击“提交”后由服务器生成差异预览：企业／记录、所属支行、表类型、期次、字段名、正式旧值、拟提交新值、变更行数。
4. 点击“确认提交”才冻结变更快照、生成变更单编号、记录基准版本，并通知本支行复核员；只打开预览不产生待办。
5. 复核员在单独的待复核页面查看同样的差异，可批准或退回。退回要求填写原因，批准可备注。
6. 批准时在一个事务内检查机构、权限、单据状态、基准行版本，更新正式数据、行版本、变更单状态、审计记录和通知事件／接收人；任一环节失败整单回滚，不能写完正式数据再单独更新审批结果。
7. 退回不改正式数据；操作员看到原因后可修改草稿重新提交。旧变更单保持不可修改，新一轮关联旧单，保留完整过程。
8. 提交后的变更快照不能原地编辑；初版建议同一人同一记录不重复提交待审变更。待审期间的新想法可在单独新草稿中保留，不能偷偷改动复核员正在看的内容。

差异预览例子仅用虚构值：

| 企业 | 字段 | 当前正式值 | 本次提交值 |
| --- | --- | --- | --- |
| 示例企业 A | 未来 6 个月是否存在违约 | 未填 | 否 |
| 示例企业 A | 后续管控分类 | 未填 | 重点关注管控 |
| 示例企业 A | 管控措施 | 原措施 | 修订措施 |

### R09：其他角色直接提交与并发冲突

复核员、支行管理员、分行管理员本人填写可直接生效；仍建议经过相同差异预览和“确认提交”，只是无需他人复核。超级管理员没有此入口。

实施步骤：

1. 所有正式写入经过唯一发布服务；角色规则决定“创建待审单”还是“直接发布”，不能在页面脚本里决定。
2. 直接提交也记录变更单、操作者、机构、旧值、新值和来源 `DIRECT_EDIT`；操作员批准生效来源为 `REVIEW_APPROVED`，导入来源为 `IMPORT`。
3. 提交与批准均携带基准版本。若填写期间管理员已改动、另一个审批已生效或导入更新了该行，禁止用旧快照静默覆盖。
4. 出现冲突时展示“原基准值／当前正式值／拟提交值”，要求重新核对生成新提交；初版整条记录版本不一致即需重新核对，不尝试自动智能合并。
5. 批量提交／审批默认整单事务成功或失败，不能前几行成功后几行报错却整体显示成功。
6. 重复点击提交、刷新回退重发、两位复核员同时审批均应幂等，只有一个有效生效结果。
7. 发布同时写入审计和通知事件；通知展示故障不能造成“正式数据已更新但没有操作记录”。

验收：操作员保存与提交前正式数据都不变；退回不改变正式数据；两人改同一条有明确冲突；重复批准不会再覆盖新数据。

### R10：修改记录查询与可追溯

实施步骤：

1. 新增独立“操作记录”页面，支持时间、机构、人员、企业／记录、模块、动作、变更单号和结果筛选。
2. 保存记录至少包含：事件 ID、服务器时间、人员 ID 及姓名快照、当时机构和角色、数据所属机构、记录 ID、期次、字段旧值／新值、动作、来源、审批人和退回原因。
3. 区分保存草稿、确认提交、直接生效、复核通过、退回、导入覆盖等动作。“每次修改”按每次保存／提交形成记录，不记录浏览器里每次按键；这是一项建议口径。
4. 业务正式变更日志按数据所属机构隔离；超级／分行管理员可查全部，支行角色仅查本支行。未提交私人草稿内容不在普通全支行日志中展开，可展示受限事件摘要；本人在自己的草稿历史查看详情。
5. 账号管理、密码重置等安全事件与业务字段变更分区，避免操作员看到不属于其权限范围的人员管理信息。密码等凭证不入日志。
6. 系统网页不提供修改／删除审计记录的功能，账号停用或人员变动后保留历史姓名及机构。

本地应用审计不等于对操作系统管理员绝对防篡改；如果后续要求正式不可抵赖审计，需要行内认可的外部审计设施，不能把普通本地日志宣传为防篡改系统。

验收：能从正式某字段追溯是谁提交、谁批准、从什么改成什么；支行不能查询其他支行日志；草稿事件不会冒充已生效修改。

### R11：每次登录的数据安全提示

实施步骤：

1. 新增独立页面，暂时只展示标题“数据安全提示”和确认按钮，正式文本以后替换，不编造条款。
2. 登录后进入受限会话；首次用户先完成改密，再确认提示，之后才能进入角色对应首页。
3. 安全提示确认状态绑定本次登录会话，重新登录再次提示，而不是账号一生只确认一次。
4. 后端对所有业务入口校验本次会话是否确认，防止直接打开下载链接、审批链接绕过。
5. 可记录确认时间和文本版本，以便未来更新正式提示；未提供文本的版本标明占位，不声称完成正式制度告知。

验收：五种角色都触发提示；未确认访问业务数据失败；退出再登录仍需确认。

### R12：新增“行内数据”模块

实施步骤：

1. 导航分成“风险预警”“行内数据”，两者共用登录、机构范围、时间筛选和导出授权。
2. 当前已提供交叉违约模板，暂归入“行内数据”，已可展示、授权填写及导出；后续其他行内表格未配置时显示空状态，不混入其他表数据。
3. 新表到位后定义表种类、机构字段、客户标识、时间字段、显示列、导出列和重复判定规则，由导入适配器负责转换。
4. 复用受机构范围约束的查询／导出服务，实现只导出当前用户可见数据。
5. 当前交叉违约黄色列 M–O 已按用户新模板纳入填报；操作员需等工作流完成后开放编辑，未知后续表不得擅自猜填报列。

验收：模块之间时间与机构筛选一致；支行导出仅含本支行；未知模板不会误导入风险预警表。

### R13：批量导入、重复识别、覆盖确认和模板

入口仅分行管理员可见，后端也仅允许分行管理员调用。超级管理员同样没有上传权限。

用户说“同步全部模块的全部数据”，本方案建议解释为：本批上传包含的各类表同步到对应模块的正式数据，全站立即使用同一份更新结果；不意味着删除没有上传的模块、其他月份或未出现在文件中的历史记录。如需要“整期全量替换”，应另设明确模式并预览删除影响，不能默认实施。

实施步骤：

1. 批量选择文件上传到临时区，创建导入任务；解析阶段不修改正式数据。
2. 按模块／表类型／模板版本识别文件及 Sheet；检查必需表头、重复表头、字段类型、期次、机构归属和允许填写值。
3. 将失败信息定位到文件、Sheet、行、列：例如缺少所属机构、日期无法识别、机构不在字典中。前端显示错误弹窗或错误页及可查看明细，不能只报“上传失败”。
4. 区分“稳定记录标识”和“重复指纹”。稳定 ID 用于审计及并发；重复指纹按模块、数据集、期次和规范化后的非填报来源字段产生，排除填报列、草稿、审批及系统技术字段。
5. 保留统一认证号、客户代码等字符串的前导零；日期、空白值的规范化必须有统一规则，不随意删掉业务上有意义的文本差异。
6. 同一来源记录但填报值不同，进入覆盖预览，显示原值、上传值、涉及条数；建议默认保留现有已填写数据，可明确选择使用上传值覆盖。
7. 上传空值覆盖已有内容也属于清空，应额外提示，不得在“覆盖”时悄悄删除填写内容。可提供逐条决定及同类冲突批量决定。
8. 同一批内的重复也要识别。相同客户同一期但来源字段变化不是用户定义的完全重复，应作为来源修订候选展示，避免误合并，也避免无提示新增一堆近似重复。
9. 对影响待复核记录的更新标记版本冲突，保留原审批单和草稿，要求复核前重新核对；不删除、不自动批准未决变更。
10. 管理员确认预览后，再次检查正式数据版本是否变化，并以整批事务提交正式数据、导入历史、覆盖决策和审计；预览期间发生变化则重新预览。重复确认不能重复导入。
11. 初版建议一个批次遇到格式错误整体不生效，先修正再上传；如未来允许部分成功，应另加显式选项及逐文件结果。
12. 为每个已经定稿的模板提供下载，标注模块、版本、字段说明和必填规则；未提供的新模板显示“待发布”，不要把现有模板冒充新版。

验收：重复上传不增重复行；有覆盖预览、取消后原数据不变；错误表不产生半批数据；导入不丢已填内容或其他月份；覆盖与待审批之间有版本检查。

### R14：离线安装、版本升级与旧 IE

实施步骤：

1. 保留 `install.sh` 一键安装／升级和 `start.sh` 前台启动；端口启动时询问、默认 2874，运行显示状态，Ctrl+C 正常关闭。
2. 迁移到新存储前停止旧服务并完整备份程序版本、配置和数据；备份放在不会被安装目录替换清理的位置。
3. 从旧 `.rows`、`.properties` 导入新库，建立稳定记录 ID 和迁移映射，逐月逐表核对行数、机构、填报值和统计；无法识别的机构应生成迁移报告并阻止误归属。
4. 旧数据没有真实修改人历史，标记“历史迁入／原始操作人未知”，不伪造历史审计。初始超级管理员身份需要本人提供并通过本地初始化设置。
5. 迁移可重复执行但不重复入库；失败保持旧程序和旧数据可恢复。数据库结构升级不能假定单个事务能回滚所有结构变更，应使用备份及版本化迁移流程。
6. 保留恢复说明及恢复检查。若升级后已经产生新业务修改，不可直接覆盖回旧快照丢弃新数据，应先保全新数据并制定回退迁移。
7. 打包包含运行时、数据库依赖、Excel 依赖、全部前端资源、校验文件、版本说明和许可证清单，不携带生产数据、账号库或初始密码。
8. 新版仍采用服务端 HTML＋普通表单为主；差异页用表格展示，提醒按钮用本地图标／文字，不要求现代单页应用能力。
9. “Win7 的 IE”不是一个精确浏览器版本。建议先按 IE8 标准模式作为最低候选基线，再依据实际版本、文档模式和行内安全配置验收。微软资料确认 Win7 环境可涉及 IE8 及旧兼容模式，不能用现代浏览器模拟结果代替实机测试。[微软 Win7／IE8 兼容说明](https://learn.microsoft.com/en-us/windows/win32/win7appqual/introduction)
10. 批量上传保留兼容方式：若旧浏览器不支持一次多选，可在同一页逐个添加文件选择框，再一次提交整批。不得因此引入 Flash 或强制安装插件。
11. 离线不等于传输加密。当前 HTTP 服务不能保护局域网中的密码传输；正式多用户投用前需由行内 IT 确认 HTTPS、证书及旧 IE 的兼容方案，不为兼容旧浏览器默认降低整个服务的安全配置。

验收：断开外网完成新装与升级；升级后账号、填报、草稿、审批、历史均保留；端口占用时明确提示；正常退出可再次启动；实际麒麟和目标 IE 跑通登录至导出的完整链路。

## 三、先统一的底层设计与接口约定

### 3.1 数据实体

| 实体 | 主要职责 |
| --- | --- |
| 机构、机构别名 | 权限边界、导入名称映射、九家支行字典 |
| 用户、会话 | 账号角色、密码、状态、改密及安全确认 |
| 权限申请、审批记录 | 开户申请、分派、审批及幂等开户 |
| 数据集定义、字段定义、导入批次 | 表类型、模板版本、列映射、来源和时间 |
| 正式记录、字段值、记录版本 | 可展示、可统计、可导出的正式业务数据 |
| 草稿、草稿字段变更 | 私人未提交修改及基准版本 |
| 变更单、变更项、复核决定 | 不可变提交快照、审批状态及差异 |
| 审计事件、通知事件、接收人 | 可追溯过程与个人已读状态 |
| 导入暂存任务、冲突决策 | 解析预览、覆盖选择、确认和提交结果 |

只建立业务需要的关系，不把每张 Excel 都硬编码成一套完全独立的权限和审核逻辑。原始来源字段和用户填报字段分开维护，但一条正式记录有统一版本。

### 3.2 已落地接口与并行前待补契约

下列区分实际类名和待实现接口，不能把方案名称当作已经存在的代码：

1. 已有 ActorContext、UserAccount、AuthService：操作者由真实登录产生，身份版本每次校验；首次改密状态在用户／会话中，安全确认尚未接入。
2. 已有 AccessPolicy：人员管理及业务动作权限，机构范围同时在仓储查询层执行，不另建一套 DataScope。
3. 已有 RecordRepository.list/find、BusinessRecord、RecordChange：带稳定 ID、版本及机构范围。
4. 已有 OfficialDataWriter.publishDirect，PR0.7 提取事务内正式写入校验供 WorkflowService.confirm／approve 复用。后者把单据、正式数据、审计及通知同事务处理；B 不得借复核员身份调用旧直接发布方法冒充审批。
5. 已有 DatasetSchema：字段键、模板列、枚举、完成口径统一维护，不另建不一致的 FieldSchema 或 CompletionPolicy。
6. PR0.7 已有实际 WorkflowService，公开 Draft／Preview／Submission／SnapshotRow 等类型；旧占位 ChangeSet 声明已替换，真实签名以 workflow-platform-api.md 为准。
7. 私人草稿、确认绑定、冻结快照、授权查询、个人通知及全部工作流事务已在公共补丁分支实现并测试；仍待评审合入 main 才放行 B1。详细约束、示例与证据见 [B1 工作流就绪清单](B1-工作流就绪清单.md)，不能将服务层通过当作网页流程已交付。
8. 已有 WorkbookImporter、ExcelExporter 和授权 HTTP 入口；业务页面复用当前服务，不假定 ImportAdapter 或 ScopedExportService 已存在。
9. 错误语义：未登录、无权限、表单失效、版本冲突、格式错误、重复请求应有明确反馈。

生产不能使用“假登录”“默认管理员”等占位实现。为并行测试提供的假用户、假时钟、假通知只允许在测试代码中使用。

## 四、两个 AI 的分工和 GitHub PR 顺序

### 4.1 推荐方案

AI A＝当前本地协作者，负责公共基础、身份权限、导入和最终集成。

AI B＝GitHub 上的另一个 AI，负责风险业务工作流、差异与复核页面、首页及清单、新模块展示。

A 先交付安全持久化和原子事务，B 同时负责工作流服务编排、页面交互和业务测试，不只是制作页面。持久化状态转换和安全校验唯一归公共层，B 不直接写 SQL、审批状态、审计或通知表。两边不重复实现审批系统；公共通知接口先行，通知中心 UI 后续由 A1 完成。

GitHub 的文本冲突经常来自同一文件同一位置的不同修改，因此先拆集中类、再落实文件所有权是本项目减少冲突的主要手段；即使 Git 显示可合并，仍需检查业务语义是否冲突。[GitHub 合并冲突说明](https://docs.github.com/en/pull-requests/reference/merge-conflicts)

### 4.2 阶段及交付

| 阶段／PR | AI A | AI B | 开始下一阶段的条件 |
| --- | --- | --- | --- |
| PR0：公共基础 | 已实现 PR0.6，审查后合入 main | 阅读方案，提供接口缺口和验收案例；暂不改公共业务文件 | PR0 合入 main，但此时 B1 仍须等公共补丁 |
| 公共契约补丁：串行前置 PR | 草稿与提交持久化、差异确认、不可变快照、通知、提交／批准／退回／直接提交事务、迁移及测试 | 只读核对契约是否覆盖 B1，用独立文档或 PR 反馈，不自行绕过接口 | 真实实现、调用示例和并发／回滚测试合入 main，就绪清单通过，记录双方共同 SHA |
| PR-A1 与 PR-B1，就绪后并行 | 复用已有账号登录，继续安全确认、权限申请、通知中心和公共审计页 | 调用公共接口组织草稿、差异、提交、复核、直接确认、冲突交互及业务测试 | A1、B1 各自测试通过；公共维护人按接入清单注册路由，合并前验证关键 HTTP 链路 |
| PR-A2 与 PR-B2，并行 | 导入暂存、重复与覆盖决策、格式错误、模板下载、授权导出服务 | 首页／明细改版、状态底色、完成率、宽屏布局、行内数据页面壳 | A2、B2 合并，跑通导入→填写→复核→统计→导出 |
| PR-C：集成与发布 | 统一检查、真实平台验收、升级回退、版本与离线包 | 复查 A 的权限／导入场景，修复自己模块问题 | 无越权、无丢数据，离线升级及实机验收通过后发布；不以合入 main 代替验收 |

不重复开发已完成的 PR0.6。先合入公共基础，再由 A 用独立 PR 补齐公共事务；B 不必等待 A1 的权限申请、安全提示及通知中心全部页面，但业务编码必须等对应基础接口可调用并通过测试。

### 4.3 分支安排

2026-09-14 修订后仅使用 main 作为 A1/B1 共同基线。公共补丁从基础分支 8c72d16 提前开始，基础 PR #1 现已合入 main；公共补丁合并后先进行用户安装测试，再安排后续业务分支：

- `codex/v0.3-foundation` → PR0 → main。main 可包含已检查的阶段性基础，不自动等同可投产版本。
- 公共维护人已从基础分支最新 SHA 创建 `codex/v0.3-workflow-platform`，实现公共补丁；先将 PR0 合入 main，再通过独立 PR 合入此补丁，避免重复合入基础内容。
- 就绪清单通过后，记录 main 的完整提交 SHA；A/B 从同一 SHA 分别建立 `codex/v0.3-access` 和 `codex/v0.3-workflow`，PR 均指向 main。
- A1 合并后，A 从最新 main 建立 `codex/v0.3-import`；B1 合并后，B 从最新 main 建立 `codex/v0.3-views`。A2、B2 可以继续并行。
- 最终在 `codex/v0.3-release` 完成发布收尾，经 PR 合入 main；正式包和发布记录另行说明验收结果，不能把测试版安装包当正式版。

依赖关系：

```text
PR0.6 → main → 公共事务补丁 → main（同一基线 SHA）
                              ├─ A1 权限／通知页 → main → A2 导入 ─┐
                              └─ B1 工作流页面／服务 → main → B2 展示 ┤
                                                                    ↓
                                                     合并、联调、升级及实机验收
                                                                    ↓
                                                         发布收尾 PR → main → 离线包
```

并行的两个业务 PR 都指向 main，不把 B 的基础直接设成 A 尚未合并的业务分支。确有接口依赖时，先提交一个小的公共接口 PR 并合并，再各自同步；不要复制另一分支代码解决依赖。

合并顺序建议 A1 → B1，A2 → B2；有完整验证且不依赖对方时可先合入已就绪的 PR，不将此顺序变成页面开发的强制串行等待。后合入者先把最新 main 合入自己的分支，跑完整相关测试再合并。已经评审的分支优先 merge 同步，不随意重写历史和强推。GitHub 支持将 base 分支变更合并或 rebase 到 PR 分支；这里选择前者作为协作默认。[GitHub 同步 PR 基线说明](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/keeping-your-pull-request-in-sync-with-the-base-branch)

同一台电脑上运行两个 AI 时使用两个独立 worktree／工作目录；如果 B 在 GitHub 云端已有独立检出目录，则各自使用自己的目录，不能在共享目录内来回切换对方分支。

### 4.5 PR 纪律与交接材料

1. 每个 PR 明确需求编号、允许修改目录、依赖的基础提交、测试命令和结果。
2. 只做当前任务，不顺手重命名全项目、不进行无关格式化、不更新另一方依赖、不擅自改共享接口。
3. 在仓库内用统一需求与接口文档交接，不靠两个 AI 的对话记忆。接口改动由 A 更新版本及示例，B 确认适配后继续。
4. 共用文件需要改动时，在 PR 评论或任务说明中给出请求，由文件负责人实施；不能以“先改了再解决冲突”为默认方式。
5. 每个 PR 附最小虚构数据测试；真实业务 Excel、账号、密码、数据库、内网证书和操作截图不进入 GitHub 或 AI 测试案例。
6. 每次合并必须同时看文本冲突、权限矩阵、状态口径、事务行为和旧 IE 能否操作。不得通过删除另一方逻辑或放宽鉴权让测试变绿。
7. A 负责最终合并与打包；B 不独立生成另一个版本号或另一套发布包。哪一个 AI 有 GitHub 写权限需执行时核实，不假定已经可以自动派工。
8. 不同电脑或 worktree 的未提交文件不自动同步。另一 AI 的就绪清单、Bash 路径修复及 Bug 记录要以独立提交／PR 交接；未知 diff 不声称已审核，不把所有文档与环境修复一概设为 PR0 合并的前置条件。工作记忆先脱敏再决定是否纳入公共文档。
9. 每次交接填写 PR、完整基线 SHA、实际 API、错误约定和测试证据。GitHub 检查因外部环境未运行时如实说明，不能用旧测试数量代替新增场景，也不绕过保护规则。
