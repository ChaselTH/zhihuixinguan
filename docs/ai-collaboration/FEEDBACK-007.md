## 1. 当前问题与代码定位

以下是维护人在 rc.8 源码确认的现状，开发者应自行复现后修复：

- `src/risk/RiskPages.java` 的 `table` 仅当 `DIRECT_EDIT && singleOrganization` 才渲染输入框，导致分行管理员选“全部支行”无法填写，操作员在本支行清单也只能看不能填。
- `src/Main.java` 的 `/update-batch` 只调用 `previewDirect`；`src/platform/WorkflowEngine.java` 的 `snapshot` 要求一单同一支行。**只放开页面条件仍会提交失败，不能作为交付。**
- `src/risk/BusinessRowPresentation.java` 逐行生成“修改并确认／填写并提交／继续我的草稿”和“查看追溯”，与新的集中操作要求不符。
- `WorkflowEngine.drafts` 只按本人／机构／表种查询，未排除已提交版本；`BusinessWorkflowState` 却另行过滤已消耗版本，两个入口口径不一致。
- `src/workflow/WorkflowRoutes.java` 恢复草稿时先取该范围全部正式行，仅在渲染时覆盖草稿值，因此草稿显示了未修改的行。
- 草稿 UI 由 `WorkflowPages` 和 `web/assets/workflow.css` 实现。用户未提供具体错位截图，需实际复现筛选栏、卡片、按钮、长文本、空态和分页布局问题，不要凭空描述已观察到的截图。

## 2. 三类清单统一在大表填写

三个数据表分别保持现有清单和模板，不是把三套不同字段拼成一张表；统一的是编辑方式。

| 角色 | 表内可修改范围 | 顶部操作与生效方式 |
| --- | --- | --- |
| 超级管理员 | 保持只读，可查看全行 | 本轮不增加业务填写／复核权限 |
| 分行管理员 | 全部支行及筛选支行的黄色字段 | 顶部“保存修改”，本人确认后直接生效，无他人复核 |
| 支行管理员、复核员 | 本支行黄色字段 | 顶部“保存修改”，本人确认后直接生效，无他人复核 |
| 操作员 | 本支行黄色字段 | 顶部“保存草稿”和“提交”，确认提交后等待本支行复核员 |

- 列表中直接显示可编辑控件，不再要求逐条点编辑按钮再去另一张编辑表。服务端逐行检查身份、机构和可编辑字段，不能只靠前端隐藏。
- 删除三类清单逐行“修改并确认”“填写并提交／继续我的草稿”和“查看追溯”入口，避免保留同类改名按钮。复核待办／提交状态可以保留必要的状态入口，不能误删复核队列和审批功能。
- 统一操作栏放在大表上方；不新增逐单元格或逐行保存按钮。普通输入、失焦、GET 查询不直接写正式库，仍由本人明确点击顶部操作触发。
- 保留原服务端差异确认、不可变提交快照及审批边界；集中预览可在顶部操作后出现，但不要再次要求逐条跳到独立编辑页。管理员和复核员无需另一人审批。
- 操作员本人已保存的草稿可在表内恢复，明确标记为“本人草稿值”；其他用户看到正式值。完成率、底色、首页统计和导出仍只用正式数据，不能因草稿覆盖展示而提前完成。
- 仅提交实际改变的行／字段，不把所有可见行当作改动；恢复原值应撤销相应草稿差异。明确区分“清空字段”与“未提交该字段”，防止漏传导致清空。
- 保留 10／20／50 条分页、上下横向滚动条、原黄色列、原下拉值和 rc.8 模板时间分期，不重新添加额外期次列。
- 翻页、改变筛选、返回及进入追溯前，未保存输入不能无提示丢失：提供保存／留在当前页等可理解提示；JS 不可用时有明确的服务端保存路径和操作说明。
- 保存草稿合并本人跨页已保存的改动，不覆盖其他页；顶部“提交”应提交当前活动草稿全部已保存差异及本页新改动，预览明确记录数、字段数和范围。管理员／复核员保存当前页的实际差异，清楚标注范围，不虚假宣称跨页未保存值已保存。

## 3. “全部支行”保存必须有完整事务能力

- 分行管理员在“全部支行”大表同时修改武进、金坛等多个机构后，顶部一次预览／确认即可保存，不能再要求手工逐支行切换。
- 建议新增受权批量直接提交能力：一次冻结当前实际差异，按真实机构划分子快照；一次确认在**一个事务**内写入全部正式值、按机构隔离的历史、审计和通知，任一冲突／异常全批不生效。
- 不允许简单循环多个独立 `confirm` 事务后把部分成功说成全部成功；不删除全局单支行校验后把跨支行内容塞进一个“CZ／第一家支行”的历史单据。
- 操作员草稿和复核单仍必须同一支行，不能借此新增跨支行提交或审批权限；支行的追溯、提交详情和通知不能暴露其他支行的子快照／差异。
- 新批量接口保持身份修订检查、服务端版本校验、确认凭据绑定、有效期、幂等、防重复确认与回滚；重复／并发点击不重复写数据、审计或通知。
- 遇到已有待复核、正式记录被导入覆盖／删除、身份变更或版本冲突，应明确提示并保留未成功提交的私人编辑，不静默覆盖旧快照或越权复用凭据。

## 4. 追溯改为支行统一入口

- 在大表上方提供一个“支行修改记录”入口，不逐行重复。已选择某支行时带入该支行；“全部支行”时在统一记录页面选择要查看的支行。
- 支行账号机构固定为自身；超级／分行管理员可选择获准支行。默认可看这家支行三类清单的全部已记录业务修改历史，分页展示，可再按清单、日期、人员等过滤，不只查询当前页企业。
- 复用公共审计／工作流记录，不另建一套重复审计表。展示谁、何时、企业／清单、改了哪些字段及前后值、提交／复核结果；私人草稿正文和 DRAFT_SAVE 不进入共享追溯。
- 保持 rc.7 规则：支行只看自身，分行管理员看所有支行但看不到超级管理员操作；超管按原规则。页码、筛选、详情链接和导出（如原有）均由服务端执行域限制。
- “全部历史”不包括已由超管明确清理的审计明细，不通过新入口复活／泄露被清理明细。旧单条路由若保留兼容仍需完整鉴权，但不是日常主入口。

## 5. 草稿生命周期与“只看我改的内容”

- 工作台“我的草稿”、全部草稿列表、数量、分页及表内状态使用统一的“本人活动草稿”规则，过滤必须在分页前完成。
- **提交成功立即移出草稿**，待复核和已通过都只在提交记录／待办出现。提交失败、确认过期或事务回滚则保留草稿，不提前移除。
- 消耗的是具体草稿版本，不能按草稿 ID 隐藏后来新的未提交版本；已提交快照不可变，也不能通过旧草稿编辑链接重写待复核内容。过期书签要指向清楚的提交状态或给出安全提示。
- 退回后保留原因和旧提交历史，由本人恢复修订；重新提交生成新不可变单据。已通过版本不能因为正式值以后又改变而重新变成活动草稿。
- 草稿只显示本人实际修改的行，摘要默认只展示必要定位信息（客户／机构／原模板时间）及修改字段的原值、草稿值；不要把全支行整期正式数据或全部未修改字段铺进草稿页。
- 恢复编辑也只加载草稿涉及行；需要新增别的行的修改时，返回统一业务大表。无差异行不计入草稿条数，最后一处恢复原值后呈现无待保存差异的空状态。
- 只读 GET 不创建、保存或重写草稿，不物理清除历史提交。另一操作员、复核员、管理员和超管都不能查看他人的私人草稿正文。

## 7. 验收清单（都需有证据）

- 三类清单 × 操作员／复核员／支行管理员／分行管理员的可编辑范围正确；超管仍只读。伪造跨支行 ID、非黄色字段、数据集和旧身份均拒绝。
- 分行“全部支行”跨两支行修改，一次确认全部成功；任一行冲突、删除或注入数据库故障全批零写入；并发／重复确认仅一次生效，各支行追溯不泄露另一家内容。
- 操作员直接在大表保存草稿、刷新恢复、顶部提交、收到本支行复核；未批准不进统计和导出，通过后才改变正式完成率，退回可修订。
- 只改 2 行时草稿只出现 2 行及真正改变的字段；其他行不出现。改后恢复原值、清空已有字段、空草稿及 10／20／50 条分页均正确。
- 第一页及第二页保存后，草稿保留两页改动；切换筛选、翻页或返回不静默丢失未保存输入；提交范围与服务端差异一致。
- 提交后工作台、草稿列表、数量、分页、表内徽标均不再把该已提交版本当草稿；失败保留、退回恢复、批准后不重现；旧草稿链接不能修改冻结快照。
- 草稿查询测试覆盖多于一页的已提交历史和活动草稿混排，不能因“先取一页再隐藏”漏掉可见草稿；不同操作员互不泄露。
- 三类表都无逐行编辑／追溯重复按钮；一个支行入口可查看该支行三类业务的修改记录，角色范围和审计清理规则不回退。
- 保留 rc.8 原模板时间分期及无额外期次列、反馈截止日期／超期色、黄色列、月份筛选、正式导出、删除标记和旧库数据。
- 必跑 `node tools/build.mjs --test --offline`、`node tests/install-smoke.mjs`；旧断言确因新需求失效时更新验收，不删除安全测试凑通过。不使用 GitHub CI。
