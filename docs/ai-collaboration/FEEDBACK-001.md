# FEEDBACK-001：权限、人员、通知及统一导入优化

日期：2026-09-16；修订：1；状态：READY；负责人：另一台电脑的 AI（原 AI B）。

从含本任务的最新 origin/main 创建 `codex/v0.3-feedback-001`。当前维护人只发布需求，不实现功能；本轮直接进入 main 的是本文档，业务代码由协作者提交 PR 后审查。不得重做旧 A/B 任务、启用 GitHub CI、改版本或自动打包发布。

## 1. 申请页面：选中效果及角色

- 分行/支行选项以背景色、边框和文字明确显示选中状态，不能仅靠颜色，保留键盘和旧 IE 核心操作。
- 分行：不显示所属支行，拟申请角色固定为分行管理员。
- 支行：选择所属支行后，必须选择“支行管理员 / 客户经理操作员 / 客户经理复核员”，不得悄悄使用错误默认值。
- 九家机构沿用：武进、金坛、溧阳、新区、经开、天宁、钟楼、营业部、中吴。认证号、姓名仍必填。
- 目标角色从申请持久化到通知、审批详情和开户；服务端校验机构/角色组合，不能信任隐藏输入。
- 迁移旧申请须保留原来能确定的目标角色；无法确定的要求确认/重新申请，不猜测提权。

## 2. 认证号全系统唯一和防重复申请

用户实测同一个认证号先申请分行再申请支行，未被阻止，需要修复。

- 认证号按字符串存储，保留前导零、去首尾空白；全系统唯一，不按角色/支行拆分唯一性。
- 已有账号或任意机构/角色待审批申请时，拒绝新申请并提示重复，不泄露其他支行详情。
- 申请、管理员新增人员、审批开户均做服务端事务/并发保护，双击、跨机构并发、建人和审批竞争只能产生一个有效身份。
- 已拒绝/撤销的申请，在没有账号/待审批申请时允许重新申请，旧历史保留。删除/停用账号不应自动重新注册成新身份，提示联系管理员恢复/处理。
- 旧库已有重复待审申请不能全部审批或静默删除；审批时兜底冲突，报告兼容/清理策略。

## 3. 必须先有对应上级管理员

| 申请角色 | 前置有效管理员和审批归属 |
| --- | --- |
| 分行管理员 | 超级管理员 |
| 支行管理员 | 分行管理员 |
| 客户经理操作员 / 复核员 | 所申请支行的支行管理员 |

- 没有有效、未删除/未停用的对应管理员，提示“当前没有所属管理员，请先联系上级管理员建立……”，服务端阻止提交，不能存成无人处理的待办。
- 其他支行管理员不能替代；超级管理员不能替代支行管理员申请所需的分行管理员；分行管理员也不能替代客户经理申请所需的本支行管理员。
- 多位合法审批人时通知对应人员，审批事务保证只开户一次；审批时重新校验授权。
- 提交后上级被删除/停用，已有申请不可丢失或转交无权人员，应有清楚异常提示/合法处理路径。
- 本条限定申请路由，不扩大现有各级人员管理范围和背对背数据访问权限。

## 4. 人员管理：初始密码再次查看、删除、密码最少 6 位

### 初始密码再次查看

用户希望审批生成的初始密码可以在人员管理重新查看，而不是仅显示一次。实现边界：

- 人员管理提供“查看初始密码”，仅有权管理该人员的管理员可主动查看，不在列表默认明文展示。支行严格隔离、禁止管理下级越权查看上级。
- 仅保留系统生成且本人尚未修改的初始/重置临时密码；首次成功改密后销毁可恢复副本，显示“已修改，请重置”。绝不提供用户自行设置的当前密码查看。
- 旧密码散列不可恢复：旧账号没有保存初始凭据时明确显示不可查看，可重置。随机生成继续使用安全随机数且建议至少 12 位；普通账号首次改密要求、超级管理员豁免不变。
- 禁止明文保存或硬编码加密密钥。需要可恢复保存时使用成熟认证加密，本地密钥受文件权限保护且不提交 Git；登录仍使用安全密码散列。
- 明确密钥与数据库备份/恢复、升级和密钥丢失处理，不能静默解密失败后显示错误密码。查看鉴权、防 CSRF、防缓存；审计只记操作与对象，日志、审计和错误中不得出现密码值。
- 环境无法安全满足时报告阻塞，不以明文存储替代。本需求不是永久保存所有用户密码。

### 删除人员

- 各级人员管理增加“删除”及确认；保持既有层级范围：超级管理员管理合法下级，分行管理员管理支行管理员/操作员/复核员，支行管理员仅管理本支行操作员/复核员。
- 不能删除自己或越权删除同级/上级，不能删除最后一个超级管理员。
- 采用逻辑删除/停用，保留历史申请、修改、提交、审批与审计；立即撤销会话，禁止再登录并清除可恢复临时密码。与原停用操作语义明确，不仅隐藏按钮。
- 删除会导致现有申请/待复核事项没有合法处理人时，阻止并提示先安排替代管理员/复核员，不静默遗失事项。

### 密码长度

- 自行改密和重设密码的页面与服务端一致：最少 6 位，保留合理上限；5 位拒绝、6 位允许、纯空白拒绝。
- 保留散列、限流、强制改密、会话撤销。首次部署初始化配置的独立安全要求不必一并放宽，说明区别。

## 5. 点击通知目标自动已读

- 点击某条通知对应链接即把本人该条通知设为已读，再进入目标；不用另点“标记已读”。气泡相应减少。
- 不得因加载列表就全部已读；重复点击幂等，禁止用他人的通知 ID 标记或获取信息。
- 保留目标授权、CSRF、跳转白名单和旧 IE 可用交互，可采用正常表单提交后重定向，不依赖现代 JS。
- 已处理/删除目标给出清晰提示，不能开放重定向或泄露越权业务内容。

## 6. 一个入口上传含三张子表的工作簿

用户改变原三入口方案：负面闭环、多重预警、交叉违约放在同一文件三个子工作表，一次上传。

- 一个上传入口、一个文件控件、一次解析预览；删除三个独立上传卡片及“旧 IE 可另选第二个文件”控件。
- 保留现代浏览器多选多个完整工作簿；旧 IE 不支持多选则一次选一个完整工作簿，也能一次导入三表，不另增备用控件。
- 保持 .et/.xls/.xlsx 离线解析；每个工作簿必须且只能各有一张匹配三套现有表头的业务子表。缺表、重复匹配、错表头明确报错；已知纯说明页可忽略。
- 表头、合并单元格、黄色列、机构、下拉值、客户编码文本及“正式黄色格任意非空即完成”不变。
- 按现有优先级处理期次：有时间顺序的表按行内期次；交叉违约按补充期次/月或可识别文件名，不用首次违约日代替。混合期次批量上传不得被一个默认月份悄悄覆盖；归属不明确先提示补充。
- 仍然仅分行管理员可上传。全部子表先解析验证，一次暂存、一次确认；批次跨所有文件/三类数据的正式写入必须原子化，任一失败全批零写入。不能分别调用三个独立提交冒充整批事务。
- 保留去重键、保留/覆盖/跳过语义、版本冲突、确认幂等、暂存过期、本人隔离、审计及草稿/待复核隔离。其他月份和本批未涉及记录不删除。
- 模板下载改成一个包含三张原格式子表的空工作簿，按需保留说明页；不加入真实数据。旧单表路由若保留兼容，仍需授权，不能形成旁路。

## 7. 解析预览只显示必要汇总

- 默认展示文件数、期次/月份、每类数据条数、新增/重复/已有填写冲突/错误数量及导入操作，不逐公司铺开明细和每个字段差异。
- 对重复项提供批量决策：默认保留已有非空填写，可选覆盖或跳过。覆盖必须确认，并提示“上传空白也会清空已有填写”。不能为了简化而静默覆盖。
- 冲突/错误按需展开；错误保留文件、子表、行、列与原因定位；有错误不能确认部分导入。
- 确认后按类型给出结果汇总，保留导入历史与审计。

## 实施顺序与授权范围

一个功能分支分阶段提交：①申请角色/去重/上级检查及并发测试；②密码生命周期、删除及迁移；③通知自动已读；④统一导入公共事务、模板、汇总页面；⑤全量验证及交接 PR。

允许修改所需身份/申请/人员/通知/导入模块、`src/platform/`、数据库迁移、`Main` 必要路由、解析/导出器、相关样式及测试/接口文档，实际路径以仓库为准。新增迁移而不改已发布迁移；验证 schema 4 旧库升级/失败回滚。不得删除用户库或读取当前维护人运行中的业务测试实例。必要备份/密钥安装兼容依赖必须说明供审查，不擅自改发布策略或制作安装包。
